# Где Solid 2 может упростить ожидание

Разбор 2026-10-26. Это список кандидатов, без изменений поведения приложения.
Проверены исходники и установленный рантайм: `solid-js@2.0.0-rc.1`,
`@solidjs/signals@2.0.0-rc.8`, `@solidjs/router@2.0.0-next.17`.
Замеров задержек и проверки в браузере в этом разборе не было.

## Ограничение перед любым переносом загрузчиков

В [solid2.md](solid2.md) уже описан сбой: повторный запрос через async memo
может дать binding внутри закрывающегося `Show` прочитать пустое значение и
остановить реактивность страницы. По прежним проверкам он проявлялся на rc.1
и rc.8; здесь исправление не проверялось и обновление зависимости не делалось.

Поэтому [createLoader](../frontend/src/hooks/loader.ts) оставляем базовым
загрузчиком данных. Он уже собирает повторы ручного кода: ключ, повторный
запрос, отбрасывание запоздалого ответа, сохранение прежнего значения при
обновлении и ошибке. `createMemo(() => fetch(...))` + `Loading` выглядит короче,
но сейчас это не достаточная причина менять работающий код.

Кроме сбоя есть различие контрактов: `isPending` в установленном рантайме —
не замена каждому `loading`. Обычный `refresh` той же задачи может быть тихим,
а `createLoader` поднимает `loading` при каждом запросе. При переносе надо
отдельно сохранить нужные индикаторы и поведение при ошибке; `Errored` вместо
сохранения старого ответа меняет пользовательское поведение.

## Что стоит делать первым

### 1. Эмодзи: одна граница для кода и готовности данных

Места: [iconSelector.tsx](../frontend/src/components/iconSelector.tsx),
[emojiPicker.tsx](../frontend/src/widgets/emojiPicker.tsx),
[emojiData.ts](../frontend/src/widgets/emojiData.ts).

Сейчас последовательность такая: открытие подменю → `lazy` загружает модуль
обёртки → её `onSettled` вызывает `ensureEmojiData` → после готовности данных
создаётся императивный `Picker`. Его перевод тоже загружается отдельно через
`emojiI18n`. Библиотека `Picker` статически импортирована самой обёрткой;
точный состав сетевых запросов определяется сборкой. Зависимость по времени
достоверна именно для запуска `ensureEmojiData` после монтирования.

Внешний `Loading` ждёт только модуль обёртки: ожидание данных и инициализации
после `onSettled` остаётся за его пределами. У `ensureEmojiData().then(...)`
нет обработчика отказа, а закэшированный `ready` после отказа не сбрасывается.
Поэтому простое повторное открытие не гарантирует новую попытку.

Кандидат: запускать чанк обёртки и готовность данных вместе по намерению
открыть подменю; перед монтированием `Picker` дождаться общей готовности,
показать локальное ожидание и ошибку. Это можно выразить общей загрузочной
функцией для `lazy`, без повторно обновляемого async memo. Оставить создание
и уничтожение custom element в lifecycle, а не переносить DOM-операции в memo.
Для ошибки определить сброс отказавшего Promise и повторную попытку.
Не переносить тяжёлые данные обратно в запуск приложения.

Проверить: холодное открытие, закрытие до готовности, повторное открытие,
ошибка данных/перевода и повторная попытка, две одновременные просьбы о данных.

### 2. Ленивые страницы и редактор: ожидание и ошибка на месте содержимого

Места: [router.tsx](../frontend/src/router.tsx),
[markdownEditor.tsx](../frontend/src/components/markdownEditor.tsx),
[sidebarSettingsButton.tsx](../frontend/src/components/sidebar/sidebarSettingsButton.tsx).

Там уже правильная основа: `lazy` + `Loading`. Дополнительный ручной загрузчик
не нужен. Но fallback пустой; при входе в редактирование preview исчезает,
пока Lexical ещё загружается. В `src` нет `Errored`/`createErrorBoundary`,
в том числе над этими компонентами: отказ чанка не получает собственной
объясняющей ошибки в интерфейсе.

Кандидат: локальное ожидание и `Errored` для страниц и редактора; при загрузке
редактора можно оставить preview как fallback. Начать с редактора и маршрутов,
а не добавлять спиннер на каждую маленькую модалку. Не прятать всю оболочку
приложения вместе с одним загружаемым участком. `preload()` по focus/намерению
войти в редактор или настройки может сократить паузу; этот API был и в Solid 1.
Сплошной preload всех страниц вернёт отложенный код в раннюю загрузку.

Проверить: первый ввод и фокус после загрузки, выход из редактирования до её
конца, отказ чанка и восстановление. Сброс error boundary и восстановление
после недоступного файла старой сборки — разные задачи; не обещать, что один
`reset` исправит отсутствующий на сервере чанк.

## Что сейчас оставляем

- [Загрузка открытой доски](../frontend/src/pages/boardPage/boardPage.tsx):
  `createLoader` отделяет fetch от применения в store и защищает от ответа
  доски, которую уже закрыли. Сокет инициирует reload. Это не просто несколько
  лишних сигналов; перенос требует сохранения этих гарантий и снятия сбоя RC.
- [Каталоги переводов](../frontend/src/i18n.tsx) и [boot](../frontend/src/main.tsx):
  язык определяется после гидрации настроек, затем каталог и `reportLanguage`
  ждутся через `Promise.all`. Ожидание до render сохраняет правильный язык
  первого кадра и даёт Go закончить смену шаблонов до чтения досок. Перенос в
  `Loading` сам по себе эту необходимую последовательность не сокращает.
- Подписки, сокеты, таймеры, нативные диалоги, сохранения и запуск агентов:
  у них свой lifecycle и семантика действий. Не превращать их в async memo
  только потому, что они возвращают Promise.

## Порядок возвращения к работе

1. Эмодзи: объединить готовность кода и данных, добавить ошибку и восстановление.
2. Редактор и маршруты: сделать ожидание и отказ чанка видимыми локально;
   оценить preload по намерению пользователя.
3. Превью шаблона и файлы: убрать оставшиеся ручные гонки через общий loader.
4. Перед переносом общих загрузчиков на async memo воспроизвести исходный
   сбой на выбранной версии Solid, затем проверить смену ключа, refresh,
   закрывающийся `Show`, ошибки и размонтирование на живой странице.

Ожидаемая польза — меньше ручной координации и понятнее ожидание/ошибки.
Снижение размера чанков из этих изменений не следует; ускорение надо измерить
отдельно на холодном открытии.
