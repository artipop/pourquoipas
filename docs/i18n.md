# Translations

Two languages are the product's own — English, because that is what the
defaults in the components say, and Russian, because that is what the app is
written for. Everything else is a catalogue somebody contributed, and none of
them is complete.

This describes what is; [localisation-plan.md](localisation-plan.md) is what is
owed — what the app writes onto a board is still Russian.

## Where a string lives

A user-facing string is a message id and an English default, written at the
place it is used:

```tsx
intl.formatMessage({id: 'Attention.dismiss', defaultMessage: 'Dismiss'})
```

`frontend/i18n/en.json` is **generated from those defaults** —
`npm run i18n-extract` walks `src/` and rewrites it, so editing it by hand is
work that the next extraction throws away. Every other file in `frontend/i18n/`
is edited: `ru.json` here, the rest by whoever translates them.

`i18n.tsx` decides which of those files the app can actually reach. A file in
`frontend/i18n/` that `getMessages` does not name is a file nobody will ever see,
and there are twenty of them, inherited.

**An id has to be a literal.** `formatjs extract` reads the source, not the run,
so an id built out of a variable — `` id: `Sidebar.${theme.id}` `` — never
reaches `en.json`, and then reads as a dead entry in every catalogue that
happens to have it. The three theme names were exactly that for a while.

## What is not a message id

Some of what a person reads is written by something other than us, and each one
needs its own locale:

- **FullCalendar** draws the month in the calendar view's title, the weekday
  headings and «ещё N» from a locale of its own, and ships with English alone
  (`components/calendar/fullCalendar.tsx`).
- **emoji-mart** names the emoji categories and its own search box. Given a
  locale and no `i18n`, it fetches the words from a CDN, which this app has no
  network for — so `widgets/emojiPicker.tsx` imports the bundle instead.
- **`Intl`** does the rest, and there is no locale to load for it: dates
  (`Utils.displayDate`, `widgets/calendar.tsx`) and everything `src/localeDates.ts`
  says — «2 часа назад» and «вчера» (`RelativeTimeFormat`), how long a span
  lasted (`NumberFormat` with a unit), the short date a person types and the day
  a week starts on. Until 2026-09-16 that was moment's, and moment said none of
  it until a 288 KB bundle of locale definitions had been fetched.

## What a board says is not a message either

The board templates this app ships are boards, not strings: their words are card
property names, column values, the setup hints, the board's prompt and the
example cards' markdown. They live in the files the boards are described in —
`internal/boardadapter/templates/*.jsonl`, plus `templates/lifetime/*.jsonl` in
the paid edition — written once, in English, the way a message id here is an
English default.

A translation is a catalogue beside them:

```
internal/boardadapter/templates/i18n/<language>.json
```

One file per language, keyed by the very string the template file carries:

```json
{
  "Development": "Разработка",
  "In progress": "В работе"
}
```

The language is the code the app's own setting uses, reduced to the language
(`ru.json` answers `ru`, `ru_RU` and `ru-RU` alike). A language with no file
there gets the templates as they are written, which is English.

The same catalogue is used for the words this app says on a board it makes in
code rather than from a file: the inbox, its view and its two fields
(`inboxWords`, `RelabelInboxBoard`), and the link field a source adds to a
board, named in the language the app was last told (`namingWords`). The guard
tests count them as template strings.

`templatetext.go` applies it at import: it walks each line of the JSONL and
replaces a string only where the JSON key is one that holds something a person
reads — `title`, `description`, `name`, `value`, `column`, `property`, `hint`,
`prompt`. That is what keeps ids, colours and the template's own slug out of
it, and it is why a catalogue may contain a word that is also an id somewhere
without any harm. A string with no translation stays as the file wrote it.

Nothing in those files is exempt: the three Russian names that used to be
(`appGivenNames`: «Исход», «прошло», «не прошло») went with the route engine
that matched on them.

### Adding or extending one

The list of strings to translate is what the guard test prints:

```
go test ./internal/boardadapter -run TestEveryTemplateStringIsTranslated
```

It names every string that has no translation in a catalogue, and its opposite,
`TestACatalogueSaysNothingTheTemplatesDoNot`, names every line that translates
something no template says any more. Both read the templates **off the disk**
rather than out of the build, because a base build embeds the paid edition's
boards nowhere and a catalogue covers every edition. So editing a template
board is what tells a translator there is work: add a column, and the test
names the word.

The templates a person is looking at are reinstalled when the language changes
(`App.relanguage`); boards they have already made are theirs and are left
alone. The inbox is the exception, because the app made it rather than the
person: its board, view and two fields are renamed into the new language
(`RelabelInboxBoard`, whose words are in the same catalogue), except a name
the person changed — which is told apart by not being any language's
translation of the app's word. When nobody has picked a language, the one that counts is the one the
page resolved from the webview's own locale and reported at boot
(`reportLanguage` in `userSettings.ts` → `App.UseLanguage`) — the Go side
cannot read it. It becomes no preference, because a resolved default is not a
choice, but it is remembered (`resolvedLanguage` in `ui-settings.json`) so that
the next launch installs the templates in it instead of installing them twice.
The page **waits** for that call before its first render: replacing the
boards takes tens of milliseconds, and a page that has already read the old
ones holds boards that no longer exist — the picker drew both languages at
once.

## What Go draws

Three things a person reads are drawn by Go rather than by the page: the menu
bar icon's menu, the OS notification about a waiting agent, and the titles of
the windows Go opens (a card's changes, the share dialog). They are drawn when
there may be no page at all — the board's window closed, the app started by a
share — so Go cannot ask for the words at that moment.

The words are still the page's. They are messages in `frontend/i18n` like every
other string (`Tray.*`, `Attention.asking*`, `CardDiff.window-title`,
`Share.title`), and `goWords.ts` formats them and hands them over through
`App.UseWords` — at boot, beside `reportLanguage`, and again whenever the
language is changed. Go keeps them in memory (`gowords.go`) and has no
catalogue: until the page has spoken, and in a server build, where there is no
menu bar, it draws with the English defaults. Receiving them redraws the menu.

A slot Go fills — the agent's name, the card's title, a count — is left in the
sentence as `{agent}`, `{title}`, `{count}`. A count needs a plural, and the
plural rule is `Intl`'s, which Go has no copy of: the page sends one sentence per
CLDR category and the category of each count up to a hundred, and Go looks the
count up. Past that it takes `other`.

The switcher between this machine's board and a server's (`attach.go`) is the
page's to draw, so there Go only says which entry is this machine (an empty id)
and the page names it (`BoardSource.this-machine`). The English title Go sends
beside it is for a page that does not know the entry.

## What Go says

Everything else Go says to a person — an error from a binding, a status, a
reason a card is standing still — is a code, its values and an English text
(`internal/apperr`). The page words the code through its own catalogue: every
code is a message `Go.<code>` in `frontend/src/goMessages.ts`, whose default is
Go's English, and `TestEveryCodeHasASentence` holds the two to each other in
both directions.

- **An error** from an `App` method: `apperr.New(code, english, name, value…)`,
  or `Wrap` with a cause, or `Kind` for a case of a sentinel that `errors.Is`
  still has to find. `Options.MarshalError` sends the first coded error in the
  chain as the rejection's `cause`, and `goError(intl, e)` words it. An error
  with no code arrives as its text.
- **A status or a reason** in a response is an `apperr.Message`
  (`{code, args, text}`), worded by `goMessage(intl, m)`.
- **A row** that keeps one (`card_stall`, `source_event`, `inbox_sort`) stores
  the English in its text column and the code and values beside it.
- A code this page does not know shows the English, and so does a message
  with no code: that is how a plugin's or an agent's own words travel.

Which errors get a code is a judgement: what a person caused or can act on —
a registry refusing a name, a folder another card holds, a login that failed.
A process that failed, a service that answered badly and anything said to an
agent is plain English.

What the app writes onto a card as a comment is still Russian, and is waiting
for a decision (`localisation-plan.md`).

## Counting

A message with a number in it is written as an ICU plural rather than as a
sentence with a number dropped into it:

```
Show {count, plural, one {# hidden group} other {# hidden groups}}
Показать {count, plural, one {# скрытую группу} few {# скрытые группы} many {# скрытых групп} other {# скрытой группы}}
```

English inflects on one boundary and Russian on three, and the three are not
where a hand-written rule puts them: 21 takes the same form as 1, and 11 does
not. `#` is the number itself. The categories are CLDR's, so a language picks
its own set — `other` alone is a complete answer for Japanese and a wrong one
for Russian — which is why a translator has to keep the `{…, plural, …}` and
not flatten it back into prose. `src/i18n.test.ts` holds English and Russian
to that; the other catalogues are on their translator.

## Handing the catalogues to a translator

```
npm run i18n-extract        # en.json ← the source
npm run i18n-table          # i18n/translations.csv ← every catalogue
```

`translations.csv` is one row per message id and one column per language the
app can switch to, English and Russian first as the reference pair. A cell is
filled where that language already has the string and empty where it does not,
so the blanks are the work. It opens in a spreadsheet as UTF-8.

What comes back goes in the same way:

```
npm run i18n-table-apply    # every catalogue ← i18n/translations.csv
```

Columns are matched by the language code in the heading rather than by
position, because a spreadsheet comes back with its columns moved and filing
Catalan under German is not a mistake anybody would catch. English and Russian
are read-only in both directions. An id the source no longer uses is dropped
from every catalogue it is applied to, which is what keeps them a subset of
`en.json`.

## Checking a catalogue

`src/i18n.test.ts` is the guard on the pair the product ships: English and
Russian have to hold the same ids and ask for the same values, and every
language the menu offers has to resolve to messages of its own. So
`npm run i18n-extract` failing the suite means a new string has no Russian yet
— which is the point.

The other catalogues are not held to that, since none of them is complete and a
test that has always failed is a test nobody reads.
