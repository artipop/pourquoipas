## Петлевые имена и проверка origin

Приложение публикуется под одним именем (`localhost:8080`), но слушает петлю
целиком, так что открыть его можно и как `http://127.0.0.1:8080`. Тогда
страница загружается, а `sameOrigin` (`frontdoor.go`) сравнивает `Origin` с
опубликованным именем как строку — и **каждый** вызов привязки отвечает 403:
ни терминала, ни настроек, ни агентов, и ни слова на экране о причине.

Этажом ниже, в `hostAllowed`, петлевые имена уже считаются одной машиной, и
переиспользовать её тут — **неверно**: у неё есть ветка «привязались к
`0.0.0.0` — принимаем любое имя на этом порту». Для `Host` это осознанное
решение (привязка к wildcard — это уже публикация в сеть), а для `Origin` —
дыра: именно эта проверка не даёт чужой странице дёргать привязки. Замерено:
с такой правкой при публикации на `0.0.0.0` проходил `Origin:
http://evil.example:8080`, а в однопользовательском режиме за ним нет и куки.
Правка была сделана и откачена (`b9a2fe5`).

Чинить — своей проверкой для origin, где wildcard-случай остаётся закрытым:

```go
func originAllowed(origin, allowedHost, allowedPort string) bool {
	parsed, err := url.Parse(origin)
	if err != nil || (parsed.Scheme != "http" && parsed.Scheme != "https") {
		return false
	}
	if parsed.Host == allowedHost {
		return true
	}
	// Только петля, и только когда дверь опубликована под петлевым именем.
	name, port, err := net.SplitHostPort(parsed.Host)
	if err != nil || port != allowedPort || !loopbackName(hostOf(allowedHost)) {
		return false
	}
	return loopbackName(name)
}
```

## Командный режим: веб-версия

Обе — про то, что страница одна, а сборки две, и в браузере она ведёт себя как
десктопная.

**Кнопка «Создать» уезжает вправо** — в браузере с вертикальными вкладками
кнопка с выпадающим списком («Обсудить с агентом» и прочее) уходит за правый
край. То есть верстка шапки считает, что ширина окна — это ширина экрана.

**Диалог «Поделиться» поехал.** Кнопка появляется только в командном режиме
(`centerPanel.tsx`), то есть до сих пор её никто не видел — и модалка под ней
свёрстана плохо: содержимое разъезжается. Это апстримовский `shareBoard`, у
которого при переносе на Solid стили не проверяли, потому что открыть его было
нечем.

**Локальное не должно предлагаться в вебе.** «Выбрать папку» и всё, что
открывает нативный диалог или работает с файловой системой этой машины, в
серверной сборке смысла не имеет: там нет окна, которому этот диалог
показывать. Сейчас такие кнопки нарисованы и падают на нажатии:

```
ERR Binding call failed: Bound method returned an error:
выбор папки недоступен в серверном режиме: впишите путь вручную
```

Сообщение честное (`pickDirectory` в `mode_server.go` говорит правду вместо
пустого пути, который выглядел бы как отменённый диалог), но человек до него
доходит только нажав кнопку, которой не должно быть. Нужен признак «эта сборка
без окна», который страница спрашивает так же, как спрашивает про привязки, — и
по нему прятать: выбор папки, открытие терминала отдельным окном и всё, что
ниже по тому же правилу. Заодно проверить, что остаётся вместо спрятанного:
у папки — поле ввода пути, у терминала — панель рядом с карточкой.

## Префикс `xciii` в ключах и именах — наполовину сделано

Имя продукта записано внутрь данных. `BoardPropColumnProperty =
"columnProperty"` — образец, но таких мест десятки: ключи автоматики на
доске (`columns`, `flows`, `prompt`, `setup`,
`git`, `branchProperty`, `projectProperty`), поля карточки
(`source`, `flow`), маркер шаблона (`template`), кука и
`localStorage` сессии (`boardSession`, `boardSessionId`), ref в git
(`refs/xciii/seen/`), ключи в системном хранилище (`xciii.probe`,
`xciii.board.machines`), id узлов на странице (`xciii-app`,
`root-portal`), имя базы (`xciii.db`), временный файл конфига MCP,
имя экземпляра миграций.

**Сделано 2026-08-20** (`5fb0a99`): ключи автоматики на доске и поля карточки
потеряли префикс совсем — `columns`, `flows`, `setup`, `prompt`, `template`,
`source`, `flow`, `columnProperty`, `branchProperty`, `projectProperty`.
Проверено, что столкнуться не с чем: в `boards.properties` сервер доски пишет
один свой ключ (`trackingTemplateId`), в `blocks.fields` — `properties`,
`contentOrder`, `icon`, `isTemplate`. Сессия переехала на `boardSession` /
`boardSessionId` — там namespace нужен, потому что куки общие на хост. Узлы
страницы стали `app-root` и `root-portal`, временный файл конфига MCP —
`mcp-config-*`.

**Осталось** — то, что является договорённостью с ОС или с уже установленными
копиями: URL-схема `xciii://` (зарегистрирована в `Info.plist` ради расширения
«Поделиться»), bundle id `io.deffun.xciii`, служба в связке ключей
(`xciii.probe`, `xciii.board.machines`, `xciii.board.address`), имя файла базы
`xciii.db` и git-ref `refs/xciii/seen/`. Их трогать стоит только вместе с
переименованием приложения. Плюс мелочь: `server/assets/templates-boardarchive/
buz8dcekwdibq3eqjq74w613rxy/board.jsonl` всё ещё носит ключи `acpColumns` —
файл устарел, собранный `templates.boardarchive` их не содержит, так что на
работу это не влияет.

Разделять их надо по тому, зачем префикс стоит.

**Он держит пространство имён** там, где наш ключ лежит в чужой карте: в
`boards.properties` и `blocks.fields` рядом с ключами форка, в связке ключей
ОС, в `refs/`. Там просто убрать его нельзя — будет столкновение.

**Он ничего не держит** в имени временного файла, в имени экземпляра
`migrate.NewWithInstance`, в id узлов страницы: это украшение.

Чинить стоит не потому, что префикс некрасив, а потому, что он называет
продукт, а имя продукта — решение, которое может смениться; после релиза
каждая такая строчка становится миграцией в своём хранилище. Сейчас релиза
нет — базы есть только у тех, кто это пишет, — и это самое дешёвое окно.

Как чинить:

- пространство имён назвать один раз (константа префикса, ключи собираются
  из неё), чтобы ответ менялся в одном месте, а не в сорока литералах;
- для хранимых ключей повторить то, что уже сделано при переходе `acp*` →
  `xciii*`: `legacyBoardProps` в `boardseed.go` читает старое написание и
  роняет его при следующей записи, так что доска мигрирует, когда её
  открыли, и ходить по базе не нужно;
- страница правится тем же изменением — `TEMPLATE_MARKER`
  (`boardTemplateSelector.tsx`), `session.ts`, `withWebSockets.tsx`, —
  иначе половина ключей разъедется;
- схема URL (`xciii://`, зарегистрирована в `Info.plist` ради расширения
  «Поделиться»), bundle id (`io.deffun.xciii`) и имя файла базы — это
  договорённости с ОС и с уже установленными копиями; их трогать отдельно
  смысла нет, они меняются только вместе с переименованием приложения.

Открытый вопрос — на что менять. «Без префикса» для ключей доски не годится
по причине выше, так что это выбор нового слова, а не удаление старого.

## Согласование версий между десктопом и сервером

Пока клиент и сервер были одним бинарём, вопроса не было. Десктоп, подключённый
к хостед-доске (`attach.go`), поставляется отдельно от неё, и ломается это в обе
стороны молча:

- **сервер старее** — `boardclient.EnsureAgentAccounts` зовёт
  `POST /teams/{id}/machine-users`, получает 404, у агентов нет учётных записей,
  и карточка не может их назвать. Наружу выходит строка из глубины стека;
- **сервер новее** — у десктопа нет `role`/`kind` в его представлении
  пользователя, и панель «Люди» покажет всех участниками. Тихо и неверно.

Согласования нет никакого: `v2` в `/api/v0` — фокалбордовская и замороженная,
под ней маршруты добавляются свободно. Есть `GET /ping` (вне `/api/v0`, без
авторизации) — ровно та форма, что у матриксовского `/_matrix/client/versions`,
— но он **врёт**: отдаёт `model.CurrentVersion` = `"8.0.0"` из мёртвого
фокалбордовского списка версий, тогда как версия приложения `appVersion` в
`version.go` — своя.

Чинить, по образцу Matrix, где это разведено на четыре механизма:

- **ручка без версии в собственном пути**, иначе ей самой не загрузиться:
  починить `/ping` (наша версия вместо чужой) и добавить туда список имён
  возможностей, которые сервер умеет;
- **возможности, а не версия**: клиент ветвится на имени, а не на номере, —
  иначе каждый бэкпорт становится ложью;
- **`clientConfig` остаётся capabilities** в матриксовом смысле («что этот
  сервер разрешает»: `teamMode`, `registrationOpen`) и с этим списком не
  смешивается;
- решить один продуктовый вопрос: расхождение **отказывает** подключению или
  **работает, громко жалуясь** в панели «Сервер». Второе честнее по отношению к
  мелочам, но требует ветки «если нет» на каждую возможность.

**И это самое дешёвое окно**: релиза нет, серверов без такой ручки не
существует. Поставить пол сейчас — один маршрут; поставить его после релиза —
ветка совместимости навсегда. Тот же довод, что у префикса `xciii` выше.

## Несколько команд на одной установке

Сейчас установка — это одна команда с id `0`, и это записано как факт в
[teamwork.md](teamwork.md). Здесь — что нужно, если делать.

Форма от форка осталась целой: у `boards` есть `team_id`, у каждой строки
`teams` свой `signup_token`, API устроен как `/teams/{teamID}/…`. Не хватает
самого содержания:

- **команду никто не создаёт**: `GetRootTeam()` жёстко берёт id `0` и заводит
  её, если её нет; страница везде говорит `Constants.globalTeamId`;
- **участия в команде нет** — нет ни таблицы, ни понятия: участие есть только
  в доске (`board_members`), а `HasPermissionToTeam` отвечает «можно» любому
  непустому пользователю на любой непустой команде, кроме управления самой
  командой;
- **`getTeamsForUser` игнорирует пользователя** и отдаёт все команды, какие
  есть в таблице.

То есть работы: создание команды, участие в ней, сужение выдачи по участию и
переключатель в боковой панели. Приглашение при этом уже командное — токен
лежит в строке команды, а не в настройках установки.

**Наследовать это не от кого.** У Mattermost облако есть, но многотенантность
там — его собственная: Focalboard в плагинном режиме брал команды, права и вход
у хозяина (следы видны до сих пор — `a.MattermostAuth` отключает `/login`,
`/register` и смену пароля с формулировкой «not permitted in plugin mode»), а
форкали мы отдельный «personal server», где команда одна. Плагинная половина из
дерева уже вынесена вместе с `ServicesAPI`, так что это работа с нуля.

**Понадобится это и без всякого облака.** Организация ставит себе одну
установку, и внутри неё команды разные — это и есть основной случай, а не
многотенантный хостинг. Так что вопрос не «нужно ли», а «что значит команда
здесь».

**И это не только про маршрутизацию.** Продукт по форме машинный: терминал —
это pty на этой машине, папка — путь на этом диске, агент — CLI, установленный
здесь. Реестры сейчас общемашинные (агенты, прокси, папки, цели деплоя), и
вторая команда упирается в вопрос, чьи они. Разумный раздел выглядит так:

- **машина владеет установкой** агента — бинарь, окружение, прокси: он один на
  всех, потому что он один на диске;
- **команда владеет тем, чем пользуется** — какие из установленных агентов ей
  доступны и какие папки ей принадлежат: две команды на одной машине почти
  наверняка работают в разных копиях кода;
- **терминалы и карточки наследуют команду от доски** — при условии, что
  проверка права смотрит на доску, а не только на живость сессии. Сегодня
  `requireSession` спрашивает «есть ли сессия», а не «чья», и это уже записано
  в [deferred.md](deferred.md), «Терминал видит любой из команды».

Пока этого раздела нет, несколько команд на одной машине — это несколько
установок; после него — одна.

## Мёртвые селекторы в стилях

Правил, к которым никто не применяется, в стилях набралось: замер на текущей
сборке — 1842 класса, из них 92 не пишет никто, и 19 живут в наших собственных
scss. Образец — `.xciii-plugin-root { height: 100% }` в `styles/main.scss`:
класс от плагинного режима внутри Mattermost, который из дерева вынесен вместе
с `ServicesAPI`, и который никто не ставит с тех пор.

Инструмент — **PurgeCSS** (`purgecss`, есть и `@fullhuman/postcss-purgecss`).
Он умеет то, что нужно: `--rejected` печатает выброшенное вместо того, чтобы
резать, а `safelist` спасает имена, которые собираются на лету.

```
cd webapp && npx purgecss --css pack/static/index-XXXX.css \
  --content 'src/**/*.tsx' 'src/**/*.ts' '../webapp/index.html' --rejected
```

Две ловушки, обе проверены:

- **имя css-файла надо брать из `pack/index.html`**, а не по маске: в
  `pack/static` лежат сборки трёх прошлых прогонов (см. соседний пункт про
  `pack`), и по маске инструмент посчитает мусор;
- **без safelist он врёт**: `icon-*` собирается как `` `icon-${name}` ``,
  `propColor*` — по имени цвета, классы вида `Foo__${kind}` — на месте. Без
  списка исключений в «мёртвые» уходит половина шрифта иконок.

Удалять по списку тоже не механически: половина имён сидит внутри перечислений
через запятую (`.propColor0, .propColor1, …`) и вложенных правил, где вырезание
одного имени ломает соседнее.

## Маршрут знает своё стойло только на своей машине

Заявку на этап десктопы уже делят: событие маршрута клеймится там, где доска
(`/acp/lease`, `acp.BoardLease`), так что двое подключённых не запустят одну
стадию дважды. Всё остальное, чем маршрут распоряжается, осталось в локальной
базе десктопа, и на доске с двумя подключёнными это врёт по-разному:

- **лимит колонки считается по своим сессиям.** `Store.RunningInColumn` читает
  `agent_session` — свою, — так что лимит в один этап пропустит по одному на
  каждую машину. Внутри одной машины это уже починено (счёт в базе, а не в
  памяти); между машинами — нет;
- **стойло видно только тому, кто его поставил.** `card_stall` локальная,
  а маршрутная полоска рисует её с Go-стороны, так что причина, по которой
  карточка стоит, не доезжает ни до второго десктопа, ни до страницы сервера;
- **возвратный бриф теряется.** Карточка, вернувшаяся на узел, получает не
  задачу, а рассказ о том, почему она вернулась (`flow_event.said`). Событие
  записала одна машина, а поднять карточку может другая — и она откроет
  разговор с пустыми руками;
- **очередь у колонки** (`stage_queue`) — то же самое: карточка ждёт места в
  очереди, которую видит один десктоп.

Чинить так же, как заявку: маршруты на серверной стороне
(`server/api/stages.go`, право `PermissionManageBoardCards`), а чтение — через
шов, чтобы локальная доска отвечала из своей базы, а серверная по HTTP. Тогда
`RunningInColumn` спрашивает доску, а не свой стор, и стойло с брифом едут с
карточкой, как и положено фактам о ней.

## База, собранная одной миграцией `000001_init`

Схема разъехалась на две миграции (`000001_board` и `000002_app`), а
`refuseOldLadder` считает «сделано нынешними» всё, что не выше второй. База,
которую построила прежняя одиночная `000001_init`, записана как версия 1 —
значит проходит проверку, и следом на неё накатывается `000002_app` поверх уже
существующих таблиц.

Проверено: приложение не поднимается, и говорит об этом так, что читать
нечего — в лог уходит весь текст миграции целиком, несколько тысяч символов,
а сообщение по делу («table `board_ref` already exists») тонет в его начале.

Воспроизводится за минуту:

```
sqlite3 "<dataDir>/server/xciii.db" "update schema_migrations set version=1;"
```

Чинить там же, где стоит отказ: на версии 1 спросить, есть ли уже таблица
приложения (`board_ref` подойдёт — её делает вторая миграция), и если есть,
отвечать тем же коротким сообщением «удалите файл базы и запустите снова»,
что и для старой лестницы. Окно узкое — так собраны только базы, сделанные
между схлопыванием лестницы и её разделением, — но стоит это десяти строк, а
разница между «удалите базу» и простынёй SQL в логе большая.

## Приглашения — один токен на всю команду

Сегодня приглашение — это `teams.signup_token`: одна ссылка на установку,
обновляемая админом, потребляемая страницей регистрации через `?t=`. Этого
хватает, чтобы позвать людей, и не хватает для трёх вещей: позвать конкретного
человека, отозвать одно приглашение, не отзывая остальные, и увидеть, кто по
какому пришёл.

Спроектировано и не сделано: таблица `invite` — `token`, `email`, `role`,
`created_by`, `expires_at`, `used_at`, `used_by`; CHECK на `role` (множество
закрыто, как у `users.role`), уникальный индекс на `token`. Регистрация
принимает оба вида токена: командный, как сейчас, и адресный, который гасится
при использовании.

## Не проверено вживую: агент над карточкой серверной доски

Проверено головой и тестами всё, кроме последнего шага: регистрация первого
(он админ), приглашение, вход участника, подключение десктопа, разделение
страницы и данных, база на двух миграциях. А вот агент, который правда
работает над карточкой серверной доски — терминал, ветка, `finish_work`,
переход по маршруту, — не запускался ни разу: для этого нужны окно и
настоящий CLI.

Порядок проверки: `wails3 task build:server` на втором порту → регистрация →
подключение десктопа в настройках → переключатель досок в боковой панели →
карточка серверной доски → «Обсудить с агентом» → стадия маршрута до
`finish_work`. Смотреть надо на три вещи, которые именно здесь и могут
разойтись: под кем подписан комментарий этапа, доехало ли имя ветки в поле
карточки, и увидел ли второй десктоп переход.

## Что нужно заполнить, чтобы ехать дальше — на самой карточке

Две кнопки исхода на маршрутной ленте («← В работе», «Деплой →») двигают
карточку в одно нажатие. Следующий шаг, продуманный только до формы: по нажатию
на «вперёд» показывать то, что **следующая** стадия объявила обязательным к
записи (`PropertyWrite.Required`), и давать заполнить прямо там.

Что за этим стоит: сегодня обязательные записи — это контракт **агентской**
стадии, проверяемый в `FinishWorkFromTools`, и человек их не видит вовсе. Когда
дальше по маршруту стоит агент, ему всё равно понадобятся эти значения — а
узнаёт он об этом, только когда попробует закончить работу и получит отказ.

Решить до кода:

- **чьи это значения.** `Writes` объявляет тот, кто пишет. «Что нужно
  следующему» — это не то же самое: читается по графу вперёд, как `reads`
  читаются назад (`UpstreamWrites`), и такой функции пока нет;
- **обязательность для человека.** Сейчас `Required` означает «`finish_work` не
  примут без этого». Если то же поле начнёт запрещать человеку двигать карточку,
  у одного флага станет два смысла и два места, где он срабатывает;
- **где рисовать.** Лента — узкая полоса под карточкой; форма на два-три поля в
  неё не встанет. Либо это раскрывающийся блок, либо кнопка ведёт в тело
  карточки к нужным полям.
